**Сопоставление с публикацией**

| Узел | Что опубликовано | Реализация и степень определённости |
|---|---|---|
| Вход / цель | 32 точки, пять признаков; следующие восемь SOC и SOH; stride 8 | Сохранено. Вход не включает исторические SOC/SOH и будущие V/I/T |
| Эксперты | SOC: 2 FEM; shared: 4 FEM; SOH: 6 FEM | Сохранено, проверяется при запуске |
| FEM | FFT, top-k положительных частот, `ceil(T/f)`, дополнение нулями, reshape | Воспроизведено по формулам 7–10; DC исключён |
| Round4 | Четыре цепочки `1×1 → grouped 3×3 → 1×1` | Каждая FEM содержит именно четыре цепочки, а не четыре отдельных эксперта |
| Агрегация FEM | Формула 12 и рисунок 3 показывают взвешивание и сумму ветвей | Используется softmax амплитуд выбранных FFT-компонент; точное соответствие аргументу `Softmax(X2D)` в формуле 12 не установлено |
| Fusion | Веса shared/task-specific зависят от входа, формулы 13–14 | Два отдельных pool+MLP+softmax модуля. Их размеры и GELU — выбранная реализация, не опубликованный конфиг |
| SOC / SOH | LSTM / Mamba, формулы 15–16 | Назначение ветвей сохранено; скрытая размерность по умолчанию 5 выбрана нами |
| Mamba | На рисунке 4: нормализация двух входных ветвей и выхода | Добавлены соответствующие RMSNorm; внешний skip отсутствует в выбранном прочтении рисунка |
| Predictor | Concatenate → 1×1 Conv → ReLU → 1×1 Conv | Сохранено. Выбор последней временной позиции и 16 выходных каналов с разделением 8/8 — явное допущение |
| Loss | Формулы 19–21; отдельные sigma из Fw | Восстановлены pool → flatten → linear → softplus для каждой задачи; loss вычисляется в FP32 |

Набор из 32 ширин FEM, четырёх групп и `top_k=4`, параметры Mamba, dropout, внутренние нелинейности FEM, детали task assessment, оси усреднения FFT и временная редукция predictor не заданы в статье полностью. Их нельзя называть «параметрами авторов».

По умолчанию внутри FEM нет GELU/dropout и дополнительного `+x`: они не указаны в опубликованной цепочке свёрток и на рисунке 3. Это буквальное прочтение схемы, а не доказательство отсутствия этих операций в неизвестном авторском коде. Настройки для отдельных ablation-экспериментов сохранены в модулях. Без дополнительных нелинейностей глубокая цепь может иметь слабые ранние градиенты; полезность такой конфигурации нужно оценивать на реальных данных. Автоматически приписывать скрытые улучшения авторам нельзя.

**Исправления данных**

1. Удалена эвристика определения единиц SOC по отдельным chunks. Для исходного KIT LOG_AGE явно задано `soc_scale=100`; метки хранятся в долях. Данные, ранее самостоятельно переведённые в доли, требуют другого явного значения.
2. Восстановлена единая семантика 30-секундных блоков: для 2s источника берутся полные временные bins, усредняются EFC/V/I/T/SOC; в bin нужны 15 корректных соседних отсчётов. Готовый 30s источник имеет приоритет. Последний SOC 2s-отсчёт не соответствует среднему SOC готового 30s LOG_AGE.
3. Временная отметка исходного LOG_AGE сдвигается с левого края на правый край блока. Таким образом вход на момент границы содержит уже завершившиеся интервалы.
4. Пропуски, недопустимые строки, неполные bins и разрывы времени разделяют сегменты. Окно не может перейти через такой разрыв или границу батареи. Дубликаты и переставленные timestamps вызывают понятную ошибку; сортировка bins не маскирует повреждение исходного порядка.
5. SOH рассчитывается из `cap_aged_est_Ah / 3.0`. Между допустимыми измерениями ёмкости используется интерполяция по времени, без экстраполяции за крайние измерения. Ось EFC не подходит для календарного старения, где она может оставаться постоянной.
6. Для anchors требуются минимум две точки; допустимая ёмкость ограничена выбранным порогом `max_soh=1.2`. Это параметр очистки данной реализации, не порог статьи. Отбрасывание точек вне покрытия anchors уменьшает число доступных окон; прежние подсчёты данных не следует переносить на v8.
7. Физическая батарея определяется парой параметра испытания и номера повторения `P+replicate`. Разделение train/val/test выполняется до scaler и исключает повтор одной батареи в разных split. Число 6/2/2 больше не зашито в проверках: для 30 батарей получается 18/6/6, для 50 — 30/10/10.
8. Статистики пяти признаков вычисляются только по train, в float64 методом объединения средних и дисперсий. Время остаётся float64 до нормализации: преждевременное преобразование большого timestamp в float32 может терять точность. На диске после нормализации — float32, цели остаются в долях.
9. Кеш v8 хранит manifest, относительные пути, scaler, сегменты, количество окон и подпись настроек/исходных файлов. Новая генерация становится активной после проверки. Подпись использует путь, размер и mtime файлов, а не полное хеширование многогигабайтных CSV.
10. В старых вспомогательных обработчиках устранены смешивание одинаковых номеров циклов разных батарей, формирование окон через NaN и часть разрывов времени. Они не превращают KIT EFC в настоящий номер цикла MIT.

Подготовка читает одну батарею целиком после проекции нужных столбцов. RAM ограничена размером обрабатываемой батареи, а не всего набора, но фиксированный предел RAM для произвольно большого одиночного CSV не гарантируется. Нормализация и проверка NPY выполняются chunks.

**Семантика KIT и отличие от эксперимента статьи**

LOG_AGE уже агрегирован и интерполирован при подготовке датасета. Поэтому этот ноутбук не может восстановить из него полностью причинный поток исходных сенсорных измерений. `soc_est` — оценка SOC, а SOH между измерениями ёмкости — разметка интерполяцией. График сравнивает прогноз с этими целевыми метками, не с независимыми измерениями состояния каждые 30 секунд.

Статья использует MIT, номинальную ёмкость 1.1 Ah, восемь обучающих батарей b1c14–b1c21, случайное выделение 20% обучающих данных под validation и две test-батареи b1c12/b1c13. Здесь KIT, номинальная ёмкость 3 Ah и validation на отдельных физических батареях. Входные `cycle`/`time` адаптированы как EFC и время эксперимента. Метрики этих экспериментов напрямую не сопоставимы.

Оффлайн-интерполяция SOH использует соседнее будущее измерение ёмкости для построения целевой разметки. Ёмкость и SOH не подаются модели на вход. Такая разметка пригодна для оффлайн-обучения, но не является онлайн-измерением SOH. Состояние Mamba сбрасывается для каждого 32-точечного окна; память не переносится по всей жизни батареи.

**Loss, обучение и выбор результатов**

Для каждого объекта сначала вычисляется MSE по восьми горизонтам:

`loss = mean(MSE_soc / (2*sigma_soc²) + MSE_soh / (2*sigma_soh²) + log1p(sigma_soc) + log1p(sigma_soh))`.

Sigma прогнозируется из соответствующего `Fw`, до LSTM/Mamba; её параметры включены в optimizer. Per-sample reduction — выбранная трактовка совместно с per-sample sigma. Публикация не детализирует все оси reduction. Добавлен численный нижний предел sigma `1e-4`. Сама функция `log(1+sigma)` математически не препятствует sigma → 0 при MSE → 0; прежнее объяснение было слишком сильным.

В train перемешиваются отдельные окна между батареями и возрастами. Gradient accumulation корректно взвешивает микробатчи по числу объектов, включая последний неполный batch и неполную группу накопления. Проверяются конечность loss/градиентов и число обработанных объектов. Логируются ошибки обеих задач, средние sigma, взвешенные составляющие loss и пропуски AMP-обновлений.

Scheduler и early stopping используют один заранее выбранный monitor. Дополнительно независимо сохраняются четыре лучших checkpoints: по joint loss, SOC RMSE, SOH RMSE и balanced RMSE. Это сохраняет удачные SOC-эпохи, даже если joint loss позже улучшился за счёт другой задачи. Выбор по joint loss сам по себе не является ошибкой для совместной задачи. Выбор по SOC нужен, когда приоритет SOC задан явно.

`last.pt` содержит модель, loss, optimizer, scheduler, GradScaler, историю, лучшие эпохи, параметры, scaler данных и RNG. Resume проверяет совместимость и продолжает с границы сохранённой эпохи. При смене модели/данных требуется новое обучение. Для test выбирается один критерий до просмотра test; сравнение test разных checkpoints с выбором лучшего исказило бы оценку.

Рост validation при падении train совместим с переобучением. По прежнему логу нельзя доказать ни единственную причину роста, ни конфликт градиентов двух задач. Разные лучшие эпохи SOC/SOH показывают несовпадение критериев качества; для диагноза нужны метрики по батареям, распределениям и составляющим loss. Большее число батарей расширяет обучающий набор, но не гарантирует заданную точность.

**Оптимизации и их пределы**

| Изменение | Что сохраняется / ограничение |
|---|---|
| Хранятся строки, собирается только текущий batch | Полная матрица всех перекрывающихся окон не создаётся; текущий batch contiguous |
| Равные FEM-периоды вычисляются один раз | Их веса суммируются; совпадение выходов и градиентов проверено для детерминированных ветвей |
| Три линейные свёртки Round объединены вычислительно | Исходные обучаемые параметры сохранены; дополнительный канал единиц сохраняет bias на краях padding; FP64-тесты проверяют все градиенты |
| Predictor вычисляется только в последней позиции | Эквивалентно вычислению 1×1 head для всех позиций с последующим выбором последней |
| Selective scan имеет serial и parallel реализации | Совпадение значений и градиентов проверено. Parallel не всегда быстрее CPU serial |
| FFT, RMSNorm, состояние SSM и loss имеют стабильные вычисления | AMP используется для подходящих операций, T4 выбирает FP16; фактический GPU путь ещё не запускался |
| CUDA selective scan подключается явно | Имена параметров общие с native; контракт типов сверен с исходниками Mamba, но расширение не тестировалось на GPU |
| Batch выбирается по измеренному full train step | Минимальный размер в пределах 5% лучшей измеренной скорости; бюджет allocated VRAM 85%; это короткий локальный probe, не гарантия для всех форм/нагрузок |

В предшествующей проверке на CPU (один поток, медиана трёх повторов) свёрточное объединение уменьшило время forward+backward новой MDEN с 244.8 до 205.5 мс при B=8 и с 1119.4 до 469.8 мс при B=64. Это сравнение двух способов вычисления одной новой архитектуры, не ускорение относительно старого ноутбука и не измерение полного обучения на T4. Исходные результаты сохранены в JSON рядом с отчётом.

Прежнее утверждение, что BF16 точно был причиной 37 секунд на batch, не было подтверждено профилированием. Исправленный выбор dtype соответствует оборудованию; единственную причину старого замедления установить по доступным данным нельзя.

**Проверка и воспроизводимость**

Фактический итог тестов и интеграционного запуска находится в `VALIDATION.json`. Выполняются реальные ячейки основного ноутбука на искусственных CSV: подготовка → обучение → checkpoints → test → шесть графических примеров. Такие данные служат проверке исполнения и индексов; их ошибки не характеризуют обученную модель на KIT. Отдельно проверены эквивалентность оптимизаций, градиенты, непрерывность окон, train-only scaler, выбор лучших эпох и восстановление checkpoint/RNG.

Реального KIT, старого пользовательского checkpoint и CUDA-устройства в среде нет. Полный запуск в интерфейсе Jupyter в предыдущей среде был заблокирован запретом локальных соединений; выполнен запуск ячеек в одном Python-процессе. Нельзя обещать ни статьевую точность, ни конкретную скорость/VRAM T4 без запуска на ваших данных.
