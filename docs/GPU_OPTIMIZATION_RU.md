# Оптимизация GPU: версия 0.4.0

Это оптимизация вычисления существующей MDEN. Размеры экспертов, признаки,
цели, FFT per_sample, loss и разделение батарей сохранены. Нового PINN-loss
в этой версии нет. Параметры сети имеют прежние имена и формы; audited
checkpoints версии 3 совместимы. При resume остаются прежние batch и AMP.

## Что изменено

1. `dynamic` — прежнее разделение batch по выбранным периодам. Полезно при
   малом batch или малом числе активных периодов; остаётся эталонным вариантом.
2. `static` — все возможные периоды определяются из длины окна. Выбор и
   взвешивание остаются на GPU, отсутствует копирование FFT-расписания на CPU.
   Выполняется больше арифметики, но устраняются ожидания CPU и переменные
   размеры подвыборок. Это кандидат, а не гарантированно более быстрый режим.
3. `matrix` — при identity/dropout=0 четыре линейных ConvRound преобразуются
   в аффинный оператор окна, затем применяются матричным умножением. Bias,
   промежуточные padding-ячейки и градиенты сохраняются. Матрицы пересчитываются
   из обучаемых параметров на каждом forward. Доступно только при T*C <= 512
   и FP32/FP64 без autocast. BF16-проверка выявила заметные расхождения с
   пошаговым округлением исходной цепочки: поэтому matrix при AMP запрещён.
4. Параметры четырёх линейных ConvRound объединяются пакетно: меньше маленьких
   операций при построении эквивалентных ядер. Первый FFT общий для входов
   трёх экспертов; дальнейшие FFT вычисляются отдельно по их признакам.
5. Native selective scan можно компилировать через torch.compile. Компилируется
   только рекуррентность; имена checkpoint, FFT-маршрутизация и LSTM не меняются.
   Компиляция выбирается, только если измеренный выигрыш превышает 5%.
   Ошибка компиляции записывается в отчёт, после чего используется eager.
6. CPU mmap-batches загружаются заранее в одном потоке, закрепляются в RAM
   и передаются через отдельный CUDA stream. Уже находящиеся на GPU данные
   проходят напрямую. Буфер ограничен несколькими batch, не размером эпохи.
7. В метриках только компактные накопители остаются FP64. Дисперсия меток
   внутри batch считается устойчивой var_mean в FP32. Обычный шаг больше
   не умножает каждый градиент на 1; для неполного накопления используется
   пакетное масштабирование. Проверки конечности loss/градиентов сохранены.
8. Fused AdamW, AMP с GradScaler для FP16, train-only scaler и кеш строк
   на GPU сохраняются из предыдущей версии. cuDNN autotuning включается
   только для фиксированных размеров static/matrix.

## Настройки ноутбука

В ячейках параметров:

```python
TARGET_RAW_GB = 10.0
FIXED_MICRO_BATCH_SIZE = None
BATCH_SIZE_CANDIDATES = (256, 512, 1024, 2048, 4096, 8192)
FEM_EXECUTION = "auto"
COMPILE_SCAN = True
AMP_DTYPE = "auto"
ALLOW_TF32 = False
MAX_VRAM_FRACTION = 0.88
GRADIENT_ACCUMULATION_STEPS = 1
```

В ячейке с количеством эпох для первой проверки выставить `NUM_EPOCHS = 3`.
Не добавлять эти присваивания выше исходных параметров: следующие ячейки их
перезапишут. Менять сами существующие присваивания.

`TARGET_RAW_GB=None` возвращает выбор по `DATASET_CELL_LIMIT` (по умолчанию 10).
При заданном объёме число батарей определяется автоматически. Выбираются
полные файлы до достижения порога, минимум три батареи. Небольшое превышение
объёма нормально. После подготовки выводятся фактическое число батарей,
разделение 60/20/20, байты CSV и NPY. Имя P+replicate определяет физическую
батарею; доступный файл 30s предпочтительнее его копии 2s. Источники без
необходимых измерений ёмкости пропускаются. Невалидные окна не выдумываются.

В автоподборе каждый допустимый режим FEM проверяется на размерах batch из
списка. В замер входят получение данных, передача, forward, loss, backward,
AdamW и метрики. Проверка выходов на реальных train-окнах идёт до замера.
Первые шаги прогревают вычисления и компиляцию. Выбирается небольшой batch
в пределах 5% от лучшей скорости данного режима, затем лучший режим.
Используется только train, веса пробных моделей не попадают в обучение.
Это ограниченный локальный поиск, а не доказательство глобального максимума.

По умолчанию auto AMP выбирает FP16 на T4 и BF16 при аппаратной поддержке
на Ampere и новее. Для сравнения матричного варианта выполнить отдельный
benchmark с `--amp float32`. Достижение 95% VRAM не является целью: важны
окна/с и отсутствие OOM на других batch. Контроль 88% относится к allocated
memory; отчёт также содержит reserved memory. Кеш данных занимает не более
25% доступного/общего объёма GPU по эвристике исходной реализации.

Настройки и результаты сохраняются в `gpu_tuning.json` и checkpoint.
Для сравнения качества фиксировать effective batch, seed и число эпох:
рост batch меняет число обновлений оптимизатора, даже при той же архитектуре.

## Проверка примерно 10 ГБ

10 ГБ здесь = 10 000 000 000 байт выбранных распакованных CSV всех split.
Это не размер архива, NPY, окон или потребление VRAM. Размер CSV существенно
зависит от интервала 2s/30s и продолжительности наблюдений, поэтому заранее
перевести его в число батарей нельзя. Примеры только для оценки: 200 МБ на
файл → около 50 батарей; 500 МБ → 20; 1 ГБ → 10.

Из корня проекта, после установки `python -m pip install -e ".[notebook,test]"`:

```bash
python scripts/inspect_data_volume.py --raw-dir "/путь/cell_log_age" --target-gb 10
```

Этот быстрый скрипт читает имена и размеры файлов, не весь CSV. Число является
предварительным: при подготовке дополнительно проверяются опорные измерения
ёмкости. Если доступно меньше 10 ГБ подходящих источников, программа явно
сообщит об этом, не подменяя объём количеством копий 2s/30s.

План проверки:

1. Запустить подготовку 10 ГБ. Проверить summary и новые графики данных.
2. Выполнить автоматический подбор в ноутбуке. Первый запуск может занять
   несколько минут; стоимость компиляции не включается в steady-state скорость.
3. Проверить устойчивость скорости на 100 шагах:

```bash
python scripts/benchmark_gpu.py --generation "/путь/generation_..." --compile-scan --stress-steps 100 --output gpu_benchmark.json
```

Здесь создаётся отдельная пробная модель; обученный checkpoint не изменяется.
Сохраняются GPU/PyTorch/CUDA, batch, AMP, режим FEM, отличие выходов от эталона,
пропущенные AMP updates, скорость и пиковая память. Для FP32-сравнения:

```bash
python scripts/benchmark_gpu.py --generation "/путь/generation_..." --amp float32 --compile-scan --output gpu_benchmark_fp32.json
```

4. Выполнить три эпохи train+validation. Проверить конечность метрик, отсутствие
   пропущенных updates, правильное число обработанных окон и сохранение моделей.
   Сравнивать RMSE и скорость с исходным режимом при одинаковом batch. Test не
   использовать для выбора execution или batch; test-ячейки выполнять после
   завершения выбора модели. Три эпохи — проверка работоспособности, не оценка
   окончательной точности.

CLI-альтернатива полному notebook:

```bash
python scripts/train_mden.py --raw-dir "/путь/cell_log_age" --target-raw-gb 10 --epochs 3 --compile-scan
```

## Проверено в доступной среде

- 47 тестов прошли на CPU; 2 CUDA-теста пропущены из-за отсутствия GPU.
- Сравнены выходы, входные и параметрические градиенты FEM: разные длины,
  padding, повторяющиеся периоды; также полная MDEN с loss.
- Проверены совместное построение ядер, повторное использование первого FFT,
  метрики на неравных batch и выбор источников по байтам с дубликатом 2s/30s.
- Ноутбук выполнен последовательно в одном Python-процессе: 37 кодовых ячеек,
  синтетические CSV, обучение, checkpoints, test и графики. Это не проверка
  интерфейса Jupyter и не измерение качества на KIT.
- CLI с выбором по размеру выполнен на синтетических CSV.

Нет измеренного ускорения на T4/GRU, проверки CUDA stream/compile на реальном
GPU или обучения на реальных 10 ГБ KIT. CUDA-тесты можно выполнить командой
`python -m pytest tests/test_gpu_optimizations.py -q` в GPU-окружении.
